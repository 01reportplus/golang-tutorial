# 38 · 项目架构、框架、运行时与持续学习

## 从变化方向划分边界

架构的价值是让常见变更局部化。HTTP 解析、业务规则、数据库访问和外部调用具有不同变化原因，可以适度分层，但不要求每个小接口都经过四五层转发。

```text
HTTP/CLI 入口 → 业务操作 → 存储或外部服务
                    ↓
                领域数据与规则
```

入口负责协议与输入格式，业务层决定规则，存储层处理持久化契约。小程序可以合并这些职责；当测试、变化或团队协作出现明确压力后再拆分。模块边界应对应真实职责，而不是照搬目录树。

## 依赖注入

构造函数显式接收数据库、客户端、时钟或小接口，通常足以完成手动依赖注入。初始化与关闭顺序在 main 中清楚可见，比把所有依赖藏进全局变量更容易测试。

接口定义在真正消费能力的一方，限制到所需方法。例如任务服务只需要 Save 和 Find，就不必依赖包含全部管理操作的大型 Repository。测试替身也应遵守真实并发与错误契约。

## 框架怎样选

| 类别 | 先理解的标准能力 | 再评估的需求 |
| --- | --- | --- |
| Web 路由 | net/http、Handler、ServeMux | 复杂绑定、生态中间件、团队习惯 |
| 数据访问 | database/sql、事务 | 生成查询、ORM、迁移与可观测性 |
| RPC | context、网络、协议演化 | 生成代码、服务治理、流式能力 |
| 微服务框架 | 配置、日志、生命周期 | 组织级规范、运维集成与学习成本 |

Gin、Echo、Chi、go-zero、GORM、sqlc 等可以作为后续研究对象，具体版本和维护状态应在选型时查官方资料。教程不以框架 API 替代语言与标准库，也不假定一个框架适合所有项目。

## 运行时知识地图

goroutine 调度与栈、内存分配器、GC、map 实现、接口表示、反射和 defer 实现共同影响运行行为。读 runtime 源码时固定版本，并先从文档和 profile 提出问题。例如“为什么切片截取后内存没降”比漫无目的浏览分配器源码更容易形成结论。

map 的具体结构、GC 算法和调度策略可能升级；不要继续把某个旧版本的桶布局、扩容阈值或停止时间当成全部 Go 版本的规则。面试解释时先说语言保证，再说带版本的实现观察。

## 常见设计模式的 Go 表达

策略可用小接口或函数，装饰器常用函数包装，选项模式可用函数式选项，观察者可用回调或 channel。模式只是组织方式，应解释它降低了哪种变更成本。

函数式选项适合可选配置较多的构造过程，但必需参数仍应显式呈现，且选项执行后统一校验。过度抽象可能让简单调用难以理解；先保持默认行为清楚。

## 算法与数据结构

学会估算时间、空间和 I/O 复杂度。使用 map 去重、切片排序、heap 管理最早截止任务、流式 Reader 处理大输入；知道数据规模后再选结构。并发不会改变低效算法的渐进复杂度，反而可能放大内存问题。

## 完成后的学习方法

选择一个生产问题建立最小复现：数据竞态、超时传播、连接池等待、错误兼容或内存保留。写下假设、证据、修复和回归检查。持续阅读发布说明，针对实际使用能力增加升级测试。

练习：把任务 API 的内存存储替换为数据库，保持 HTTP 契约测试不变；说明新增接口解决了哪一个具体替换问题；为后台投递任务设计应用级关闭顺序。
