# 23 · 内存模型与 happens-before

## 共享内存需要顺序依据

一个 goroutine 写入变量，另一个 goroutine 读取，不能仅靠“通常先执行”推断读到新值。编译器、CPU 和调度器只需遵守语言与同步契约；正确程序应通过同步建立可观察顺序。

数据竞态是并发访问同一内存位置且至少一方写入、没有合适同步的情况。即使一个平台上看似原子的单字写入，也不能让普通变量读写自动满足 Go 的并发语义。

## happens-before 的作用

可以把它理解为由程序内顺序和同步关系共同建立的偏序。没有竞态的程序具有更容易推理的顺序一致性行为。普通开发者应优先使用锁和 channel，而不是尝试以睡眠或调度器碰巧让出实现可见性。

```go
package main

import "fmt"

func main() {
    done := make(chan struct{})
    var message string
    go func() {
        message = "ready"
        close(done)
    }()
    <-done
    fmt.Println(message)
}
```

message 的写入发生在 close 前，关闭通知与读取建立同步关系，因此 main 可以在接收后读取。若删除 channel，只换成 Sleep，就失去了这种依据。

## 常用同步边界

Mutex 的解锁与后续成功加锁形成文档规定的同步关系。channel 发送与相应接收建立关系，关闭与观察关闭的接收建立关系。WaitGroup 的 Done 与对应 Wait 返回、Once 完成与其他调用返回、原子操作之间也有各自契约。

这些关系应按具体 API 推理，不能概括为“只要出现过 channel，所有变量都安全”。发送指针后继续修改指向对象，仍可能与接收方竞争。

## 安全发布与不可变快照

先完整构造对象，再通过锁、channel 或 atomic 发布，读者读取后不再修改，可以简化共享设计。初始化顺序正确并不保证发布后的修改安全；对象里含 map 时尤其要检查是否有人继续写。

双重检查锁如果在锁外读取普通变量，仍可能有竞态。用 sync.Once、锁或正确原子发布代替自行猜测。把指针转为 uintptr 也不会获得同步或生命周期保证。

## race 检测与限制

```sh
go test -race -count=1 ./...
```

检测器观察实际执行路径，增加测试覆盖和并发变化能提高发现概率。但结果不涵盖所有可能执行，也不检查数据库事务隔离、跨进程顺序或业务幂等。

非数据竞态问题同样重要：两个 goroutine 即使使用锁，也可能以错误业务顺序操作；正确加锁的队列也可能无界增长；没有竞争的程序仍可能死锁。内存安全和业务正确性需要分别验证。
