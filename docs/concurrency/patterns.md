# 22 · 工作池、流水线、限流与背压

## 从资源约束选择模式

并发模式不是必须套用的模板。先确定瓶颈：CPU、连接数、第三方配额、内存还是结果顺序。再明确最大活跃任务数、排队长度、取消方式、失败策略和输出顺序。

| 需求 | 常见方式 | 必须补充的契约 |
| --- | --- | --- |
| 限制活跃任务 | 固定 worker 或信号量 | 获取名额能否取消 |
| 多阶段处理 | channel 流水线 | 哪个阶段关闭输出 |
| 合并结果 | fan-in | 所有发送者何时退出 |
| 读多写少配置 | 只读快照 | 发布后不可修改 |
| 限制每秒调用 | 令牌桶等限流器 | 突发容量与拒绝策略 |

## 工作池

固定数量 worker 从 jobs 接收任务，将结果写到 results。一个协调者负责投递，一个协调者等待 worker 完成并关闭 results。投递和结果发送都要响应取消，否则消费者提前退出时仍会泄漏。

```go
select {
case jobs <- job:
case <-ctx.Done():
    return ctx.Err()
}
```

只在 worker 里检查 ctx 不够，因为生产者也可能卡在发送。若使用信号量，应在启动 goroutine 前取得名额，否则先启动百万个任务再让它们等待信号量，仍然有百万个 goroutine。

## 背压与有界队列

下游变慢时，让上游等待就是背压。缓冲只是暂存突发流量；生产率长期大于消费率时，任何有限缓冲都会耗尽。需要选择等待、拒绝、丢弃、降采样或持久化排队，而不是持续增大 channel 容量。

队列同时也是延迟来源。队列越长，任务可能在开始前就已过期，因此开始处理前应检查截止时间。把队列长度、等待时间和拒绝次数作为监控指标，比只看 CPU 更容易判断过载。

## 错误传播

“第一个错误取消其余任务”和“收集全部错误”是不同需求。前者适合整体不可分割的并行子任务；后者适合批处理报告。返回部分结果时要写清楚其是否完整、顺序是否稳定、取消是否导致数据丢失。

`golang.org/x/sync/errgroup` 是常用第三方扩展包，可结合 context 管理错误与等待；使用前查当前文档和版本。SetLimit 限制活跃 goroutine，但仍需理解提交与取消的交互。

## 顺序与幂等

并发完成顺序通常不同于输入顺序。需要稳定输出时携带原索引并在协调阶段归位，而不是让 worker 争抢一个共享 append。给共享切片的不同既定索引写入可以成立，但前提是无重叠、没有同时修改切片头，并在读取前正确等待。

重试需要识别暂时性错误、总预算、退避、抖动和幂等条件。限流限制速率，信号量限制同时在途数，两者解决的问题不同，常需要组合。
