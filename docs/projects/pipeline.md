# 41 · 实战三：有界并发与可取消流水线

## 需求

输入一组值，用固定并发度处理，按原始输入顺序返回结果。遇到第一个错误或父 context 取消时，通知其他工作停止，并等待所有已启动 worker 退出；失败时不返回部分结果。处理函数必须响应 context，并且不能 panic。

这比无界 `go fn(x)` 多了三个必须验证的契约：活跃调用不超过上限，完成顺序不影响输出顺序，取消后没有还在发送结果的后台任务。

go run ./examples/pipeline
go test -v ./internal/pipeline

jobs 只传输入索引，不传共享可变任务结构。worker 读取 inputs[index]，计算后写入 out[index]；每个索引只投递一次，因此各 worker 写入不同元素。主流程在 Wait 返回后读取，建立完成与可见性关系。

唯一投递方关闭 jobs，worker 不负责 close。没有单独结果 channel，也就没有消费者提前退出后无人接收结果的问题。生产投递仍需 select ctx.Done，否则所有 worker 退出后投递方可能永远阻塞。

## 错误与取消

WithCancelCause 保存取消原因，第一个失败触发 cancel(err)，其他 worker 在下一次工作前或处理函数内部检查 ctx。主流程结束投递、关闭 jobs 并等待 worker，最后返回 context.Cause。

取消是协作性的：如果 fn 永久卡在不支持取消的调用，Map 也无法强制结束。函数文档必须清楚说明这个前提。真实网络调用要把 ctx 交给底层 API，同时设置适当 I/O deadline。

如果取消和某个成功结果几乎同时发生，部分结果可能已经算出；本契约选择失败时整体返回 nil 和 error，避免调用者误把不完整结果当完整。需要保留部分成功结果的批处理，应设计另一种结果类型并明确缺失状态。

## 测试为什么不用随机 sleep

并发上限测试用 started 通知确保两个 worker 都已开始，再关闭 release 让工作继续；atomic 计数记录峰值，断言等于 2。这样验证的是明确状态，不是“睡一会应该正在并发”。

取消测试等待工作确实开始后再取消，观察 Map 返回 context.Canceled。测试中的 3 秒 timer 只作为故障时的有界保护，不用于安排正确执行次序。空输入、非法并发数、nil 函数与处理错误也有测试。

## 复杂度与限制

最多 min(workers, N) 个 worker，结果切片 O(N)。这不是无限数据流接口，因为全部输入和结果保存在内存中。需要真正流式处理时，应设计 channel 或迭代器输出，同时重新处理消费者取消、输出关闭与背压。

共享 fn 捕获的外部状态仍需由调用者保证线程安全；Map 只保护自己的调度契约。传入指针或切片元素时，也不能假设深拷贝隔离。

## 扩展练习

把 fn 换成带 context 的 HTTP 请求，在本地 httptest 服务上测试慢响应与错误；增加限速器，区分每秒请求数和同时在途数；提供“全部错误汇总”版本，解释它为什么不应复用遇错即取消的契约。
