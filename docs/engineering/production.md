# 33 · 配置、结构化日志、可观测性与服务安全

## 配置需要类型与校验

配置来源可以是 flag、环境变量或文件，必须明确优先级。启动时解析为有类型结构，校验端口、URL、超时和并发上限；不要在每个请求中重新读取环境变量。必需配置缺失应明确失败，而不是静默采用危险默认值。

密钥通过部署系统注入，避免进入 Git、镜像层和日志。日志输出配置时，应只展示非敏感字段。配置热更新需要原子发布完整快照，不要让读者观察到更新一半的结构体。

## slog 结构化日志

```go
logger := slog.New(slog.NewJSONHandler(os.Stderr, nil))
logger.InfoContext(ctx, "创建任务",
    "request_id", requestID,
    "task_id", task.ID,
    "duration_ms", elapsed.Milliseconds())
```

稳定字段便于搜索和聚合。日志级别按事件意义选择：客户端参数错误通常不是系统故障；重试中的预期失败与最终失败应区分。不要让每层都打印同一错误，保留完整上下文并在有决策权的边界记录。

日志也会占用磁盘、网络和 CPU，需控制大对象、堆栈和高频事件。用户文本要作为字段值处理，避免自行拼接造成日志伪造或不可解析输出。

## 日志、指标与追踪

日志回答某次事件发生什么，指标观察总体趋势，追踪串联跨服务请求。请求 ID 不等于完整追踪系统。指标 label 应低基数，不能把每个用户 ID、URL 查询串或错误全文作为标签。

常见指标包括请求速率、错误率、延迟、队列长度、活跃任务、数据库等待和内存。区分存活检查与就绪检查：进程活着不表示可以接收流量，而短暂下游故障也未必应该让进程反复重启。

## 输入与资源边界

安全设计先限制资源：body 大小、文本长度、分页大小、并发数、队列长度、查询时间和上传文件数。认证确认是谁，授权确认能做什么；二者不能仅靠前端隐藏按钮实现。

SQL 使用参数化查询；HTML 使用上下文转义；路径访问限制根目录并考虑符号链接；出站 URL 限制 scheme、目标地址和重定向，防止 SSRF。验证不能只做在表面字符串上，实际解析与使用环节必须保持同一语义。

## 密码学与认证

安全随机使用 crypto/rand。哈希不等于加密，base64 也不是加密。密码存储应使用经过审查的专用密码哈希方案与参数，不使用普通 SHA256 直接保存密码。证书校验、token 生命周期、密钥轮换与会话撤销需要结合系统需求设计。

认证中间件不自动实现租户隔离；查询与更新必须绑定授权范围，防止仅凭任意资源 ID 读取他人数据。

## 依赖和运行环境

```sh
go version -m ./your-binary
govulncheck ./...
```

govulncheck 是独立工具，需按官方说明安装合适版本。扫描结果应结合可达调用、部署版本和补丁状态评估；没有发现也不代表不存在漏洞。

容器优先非 root，按需提供 CA 和时区数据，避免把诊断端口与管理端口公开。更新依赖和 Go 补丁版本后运行测试，再按部署策略验证与回滚。

## 优雅停机

停止接收新流量，给正在处理的工作一个有界时间完成，取消剩余任务，等待 goroutine 退出，再关闭连接池与日志输出。关闭顺序应与依赖关系相反。不能在数据库关闭后还允许后台 worker 提交任务。

练习：为 API 增加请求 ID 与耗时日志；设计一组不会含用户 ID 的指标标签；列出从输入接收到数据库写入之间的授权检查点。
