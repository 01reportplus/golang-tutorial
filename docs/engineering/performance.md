# 32 · 性能分析、GC、逃逸与运行时诊断

## 先定义性能问题

性能目标必须带工作负载：在多少并发、数据量和硬件下，吞吐、延迟分位数、内存或 CPU 达到什么要求。平均延迟会掩盖长尾，单请求更快也可能以更高峰值内存为代价。

先测量基线，再提出假设、修改一个因素、重复测量。应保存版本、输入和构建参数，让别人可以复现。不要把“少写了一次分配”直接等同于用户感知速度提升。

## CPU 与内存 profile

```sh
go test ./internal/wordcount -run '^$' -bench . -cpuprofile cpu.prof
go tool pprof cpu.prof
go test ./internal/wordcount -run '^$' -bench . -memprofile mem.prof
go tool pprof -alloc_space mem.prof
```

CPU profile 展示采样期间运行时间，不能直接解释所有等待；内存 profile 可看累计分配或当前保留，要选对视图。高分配不一定高保留，低保留也可能带来持续 GC 压力。

服务可以通过受保护诊断入口提供 net/http/pprof。不要把默认诊断路由无条件暴露公网；profile 与 goroutine 栈可能泄露业务路径和数据线索。

## 阻塞、锁与 trace

请求变慢而 CPU 不高时，检查连接池、锁、channel、网络和磁盘等待。阻塞 profile、Mutex profile 和执行 trace 提供不同角度。trace 能看 goroutine 状态与调度事件，适合分析排队和长时间停止推进。

开启诊断有成本，生产采样应有时间边界和访问控制。先缩小到一个典型时间窗口，再深入分析，比持续收集海量数据更可控。

## GC 的基本模型

GC 回收不可达对象，不回收仍被 map、闭包、切片底层数组或 goroutine 引用的数据。分配速率、存活堆大小和指针数量共同影响 GC 工作。垃圾回收也有 CPU 与暂停成本，不能只看“有 GC 所以简单”。

GOGC 控制增长目标相关策略，GOMEMLIMIT 提供软内存限制。它不是操作系统硬限制，不涵盖所有外部内存，也不能保证绝不 OOM。容器要给 runtime、栈、cgo、映射和系统开销保留空间。

## 逃逸分析与内联

```sh
go build -gcflags='-m=2' ./cmd/wordcount
```

编译器据对象是否可能在函数之外被访问等因素决定分配位置。闭包、接口转换和大对象都可能影响结果，但每个现象要用当前编译器验证。new 不等于必然堆分配，指针也不等于必然高性能。

优化过度追求“零分配”可能引入别名、复用和并发错误。可读、边界清楚的代码是有效基线，只有热点需要增加复杂度。

## 从症状到工具的实验路线

| 症状 | 第一组证据 | 下一步判断 |
| --- | --- | --- |
| CPU 持续偏高 | CPU profile、请求量 | 热点是算法、编码还是忙循环？ |
| 请求慢但 CPU 低 | trace、阻塞和连接池指标 | 时间花在锁、排队还是远程 I/O？ |
| 堆持续增长 | inuse_space、对象数量 | 是缓存设计、底层数组还是后台任务保留？ |
| 分配频繁但堆不大 | alloc_space、allocs/op | 能否减少临时转换或重复解析？ |
| RSS 高于 Go 堆 | 系统内存、cgo、mmap 与栈 | 是否有 Go 堆外分配或尚未归还内存？ |

例如服务在低流量下也占满一个核，先看 CPU profile，若热点集中在 select 的 default 附近，检查是否忙等；不要先调整 GOGC。若延迟主要来自数据库连接等待，增加 goroutine 可能进一步恶化队列，应先分析连接与查询预算。

## 分配器和 GC 的阅读边界

当前 runtime 会按对象大小、指针特性等选择分配路径，使用线程/处理器相关缓存与更大范围结构减少竞争。具体尺寸分类、tiny 对象规则和回收策略都是带版本的实现。理解“为什么存在分层缓存”和“为什么指针扫描有成本”比背某一版本全部常量更有用。

Go 1.26 的 GC 实现已有更新，历史文章中的性能与暂停数字不能直接套用。GOGC 调低通常让 GC 更频繁，可能降低堆增长却增加 CPU；调高可能相反。先控制无界缓存和分配源，再在生产相似负载下调参。

## 常见优化方向

减少重复解析与重复编码，适当预分配切片，复用 HTTP Transport，批量数据库写入，避免 N+1 查询，有界并发，减少锁内 I/O。对缓冲池设置最大容量，避免一次大请求让池长期保留巨型内存。

PGO 可利用代表性 profile 反馈优化构建；是否有收益要在相同环境测量。更换算法或减少网络往返通常比局部微优化更重要，但仍需证据支持。

## 故障诊断

goroutine 数持续增长时查栈和生命周期；RSS 增长时区分 Go 堆、栈、mmap、cgo 与系统缓存；CPU 高时看热点与忙循环；延迟抖动时同时观察 GC、调度、下游与队列。单一指标不足以下结论。
