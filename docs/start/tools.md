# 04 · Go 工具链与调试

## 形成短反馈循环

每次修改后先格式化，再运行最小相关测试，最后运行包级检查。`gofmt` 负责语法格式；`go vet` 通过静态分析发现可疑代码；`go test` 验证行为。它们解决不同问题，任何一个通过都不是正确性的完整证明。

```sh
gofmt -w main.go
go vet ./...
go test ./...
go test ./internal/taskapi -run TestCreate -v
go doc strings.Fields
go list ./...
go env
```

`./...` 递归匹配当前 module 内的包，通常不跨越嵌套 module。不要为了“能运行”在子目录反复创建 `go.mod`，否则根目录检查可能漏掉代码。

## 测试输出怎样读

测试名从 `Test` 开始，失败信息应给出实际结果与期望。`-v` 显示详细过程，`-count=1` 禁用测试结果缓存，`-run` 用正则筛选测试。性能基准用 `-bench`，数据竞态用 `-race`；这些参数各有前提，详见测试与诊断章节。

看到 `(cached)` 表示工具链复用上次成功结果。怀疑状态问题时先理解缓存条件，再用 `-count=1` 复现，不必习惯性清空所有缓存。

## 调试器与日志

调试器可以设置断点、查看局部变量、调用栈和 goroutine 状态。Delve 是 Go 常用调试器，编辑器通常集成它。优化和内联可能改变变量可见性，调试构建可按工具说明关闭优化。不要在生产进程上随意长时间暂停线程，暂停会改变超时和并发行为。

日志适合记录事件经过，调试器适合观察一个执行点，profile 和 trace 适合定位性能问题。先写下问题，再选工具，例如“CPU 时间花在哪里”和“请求为什么等待”需要的证据不同。

## 编译器与运行时诊断

```sh
go build -gcflags='-m=2' ./cmd/wordcount
go test -bench . -benchmem ./internal/wordcount
go test -cover ./...
```

逃逸分析输出说明编译器当前选择；不要把一次构建的结果当作语言保证。覆盖率只说明测试执行过哪些语句，不能证明边界值、并发次序或结果断言充分。

`go version -m` 可查看可执行文件的构建信息。排查用户环境问题时，收集版本、平台、命令、最小输入与错误原文，远比只提供截图中的一句“运行失败”更有效。

## 常用 Git 工作方式

把代码、文档、`go.mod`、必要的 `go.sum` 和工作流提交到仓库，忽略二进制、虚拟环境、构建站点和本地数据。提交前看 `git diff`，确认没有 token、临时输出或意外删除。本教程 Pages 发布流程只上传生成的静态文件，文章仍以 Markdown 作为维护源。

练习：故意让 `Printf("%d", "go")` 进入程序，分别观察编辑器、`go vet` 与编译器如何报告；再创建一个断言失败的测试，练习缩小复现范围。
